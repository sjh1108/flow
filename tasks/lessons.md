# Lessons

사용자 지적으로 바로잡은 패턴을 누적한다. 세션 시작 시 이 파일을 먼저 읽는다.
새 항목은 **패턴 → 왜 놓쳤나 → 규칙** 순서로 쓴다. 한 줄 요약은 쓰지 않는다 —
다시 읽었을 때 같은 실수를 막을 만큼 구체적이어야 한다.

---

## 1. 픽스처가 규칙을 우회하면 그 규칙은 검증되지 않는다

**패턴** — R5(실행 파일 내용 검사)가 `exe` 체크박스를 무력화하는 버그가 있었는데
137건의 테스트가 전부 통과했다.

**왜 놓쳤나** — 통합 테스트·`verify.sh`·브라우저 테스트의 **모든 `hello.exe`
픽스처 내용이 텍스트**(`"hello, world"`)였다. PE 시그니처 바이트를 한 번도 쓰지
않아 해당 분기에 진입조차 하지 않았다. 테스트 수가 많다는 것과 올바른 것을
검증한다는 것은 다르다.

**규칙** — 어떤 규칙을 테스트할 때 **그 규칙이 실제로 발동하는 입력인지** 먼저
확인한다. 실행 파일 관련 테스트에는 반드시 실제 시그니처 바이트를 쓴다.

---

## 2. 같은 값을 여러 문서에 복사하면 반드시 어긋난다

**패턴** — 테스트 건수가 README·추적표·도구·배포 문서 네 곳에 하드코딩되어
**세 번 어긋났다.** 두 번째 정정 때 "한 곳에서만 관리한다"고 PR 본문에 적었지만
저장소는 그대로 네 곳이어서, 문서의 주장과 저장소가 반대인 상태가 됐다.

**규칙** — 같은 사실이 두 곳 이상에 적히려 하면 멈추고 단일 출처를 정한다.
"앞으로 잘 관리하겠다"는 해결책이 아니다. 구조를 바꾼다.

---

## 3. 확률적 휴리스틱을 구조적 보장처럼 서술하지 않는다

**패턴** — `CAFEBABE`를 Java class와 Mach-O fat으로 구분하면서 "두 형식의 바이트
4-7이 **구조적으로 겹치지 않는다**"고 코드 주석·문서·PR 본문에 적었다. 사실이
아니었다. Apple 명세는 `nfat_arch`에 상한을 두지 않아 같은 4바이트가 양쪽으로 다
해석된다. 실제로는 `52 >= 45`라는 추측이었고, 공격자는 값을 골라 우회할 수 있었다.

**왜 놓쳤나** — "현실의 fat 바이너리는 아키텍처가 2~6개"라는 **관찰**을 **제약**으로
바꿔 적었다. 보안 규칙에서 공격자가 자유롭게 고르는 값에 기대면 방어 가치가 없다.

**규칙** — "구조적으로", "명세상", "불가능하다"를 쓰기 전에 **명세 원문의 제약을
확인**한다. 확인할 수 없으면 "휴리스틱"이라고 쓴다. 모호하면 거부한다.

---

## 4. 넓은 패턴으로 다시 훑기 전까지 "전부 고쳤다"고 말하지 않는다

**패턴** — "진짜 PE 파일" 표현이 과장이라는 지적을 받고 정정한 뒤 "전부 고쳤다"고
답했으나, `real PE`만 grep해서 `real executable` / `genuine executable`을 놓쳤다.

**규칙** — 일괄 정정 후에는 **동의어를 포함한 넓은 정규식**으로 다시 훑고 0건을
확인한 뒤에 완료를 보고한다. (예: `(real|genuine|actual)[ -]+(pe|executable|binary)`)

---

## 5. 실행 중인 프로세스가 방금 빌드한 코드라고 가정하지 않는다

**패턴** — `.out` 제거를 실행 중인 API로 확인했더니 `ACCEPTED`가 나왔다. 이전
세션의 jar가 8080을 계속 점유해 새 인스턴스가 바인딩에 실패했고, **옛 코드를
검증하고 있었다.** stale jar 기준으로 "통과"를 보고할 뻔했다.

**규칙** — API를 대상으로 검증하기 전에 포트를 점유한 프로세스를 정리하고, 의심스러우면
**빌드 산출물에서 변경 사항을 직접 확인**한다
(`unzip -p app.jar BOOT-INF/classes/....class | strings | grep ...`).
`pkill -f <pattern>`은 자기 명령줄에 매칭되어 셸을 죽일 수 있으니 PID로 죽인다.

---

## 6. 일반 원칙으로 묶으면 오류가 숨는다

**패턴** — `DECLARING_EXTENSIONS`에 `msi`를 "설치 관련 실행 파일이니까"로 넣었다.
MSI는 OLE 복합 문서라 PE가 아니고, PE 내용 + `evil.msi` 경로가 성립했다. 같은
성격으로 `bin`, `out`도 발견됐다.

**규칙** — 목록에 항목을 추가할 때 **그 항목이 조건을 실제로 만족하는지 개별로**
확인한다. "같은 계열이니까"는 근거가 아니다. 기준을 정했으면 예외를 만들지 않는다 —
예외 하나가 기준 전체를 무너뜨린다.
