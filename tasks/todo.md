## 현재: DB 권한 분리 실효화 (PR #5)

**계정을 나눈 것과 분리한 것은 다르다.** 앱 컨테이너가 `SPRING_FLYWAY_PASSWORD`로
마이그레이터(`ALL PRIVILEGES`) 자격증명을 들고 있었으므로, 앱을 장악한 쪽은 자기
환경변수를 읽어 그 계정으로 붙으면 그만이었다. `grants.sql`이 막겠다고 적어둔 위협
모델이 정확히 그 경우다.

- [x] 마이그레이션을 `migrate` 프로파일의 one-shot 컨테이너로 분리.
      앱에서 `SPRING_FLYWAY_*` 제거, `SPRING_FLYWAY_ENABLED=false`
- [x] 종료를 데몬 스레드에 맡기지 않고 `System.exit(SpringApplication.exit(...))`로 명시
- [x] `grants`를 one-shot 서비스로 자동화. 매 배포마다 재적용
- [x] 순서가 바뀌어 임시 광범위 권한이 불필요해짐 — **앱 계정이 단 한 순간도
      `extguard.*` 전체 권한을 갖지 않음**
- [x] `01-users.sql` → `01-users.sh`. 비밀번호를 커밋된 파일에서 제거하고 형식 검사
- [x] V4 인덱스 — `(status, purged_at, created_at, id, size_bytes)` (PR #4에서 넘긴 후속)

### 계획에 없었는데 발견한 것

`grants.sql`이 `mysql-init/`에 있어 `/docker-entrypoint-initdb.d`로 마운트되고 있었다.
그 디렉터리는 **DB 최초 기동 시** 실행되는데 그때는 테이블이 없어 테이블 단위 GRANT가
불가능하다. README는 이 파일을 "마이그레이션 이후 수동 실행"이라고 안내하고 있었으니,
처음부터 그 자리에 있으면 안 되는 파일이었다.

### 리뷰 대응 — 7건

**세 번 같은 형태였다: 주장은 있는데 그 주장을 재는 것이 없었다.**

- [x] **CI가 H2만 돌아 이 PR의 핵심을 검증하지 못했다.** 나는 "Docker 데몬이 없어
      확인하지 못했다"를 PR 본문에 한계로 적고 끝냈는데, **CI 러너에는 Docker가 있었다.**
      미확인으로 남긴 목록이 바로 이 PR이 주장하는 전부였다 →
      `scripts/verify-grants.sh` + `Database privilege boundary` job
- [x] **첫 CI 실행이 빈틈을 하나 더 드러냈다** — 새 DB에서만 돌아 "제거한다"가 시험되지
      않았다. 지울 것이 없으니 통과가 당연했는데 그게 `REVOKE` 지적의 핵심이었다 → 5절
- [x] **그 검증조차 핵심을 비껴갔다** — health가 올라온 것은 앱이 돈다는 증거일 뿐이다.
      `SPRING_FLYWAY_PASSWORD`를 다시 넣어도 전부 통과한다 → `docker inspect`로
      자격증명 분리 자체를 단언. 이름이 아니라 **값**까지 본다
- [x] `REVOKE`를 `ON` 절 없는 전역 형식으로 — DB 레벨만 비우던 것을 테이블·컬럼까지
- [x] `fixed_extension_state`의 UPDATE를 `(blocked, updated_at)` 컬럼 단위로.
      **이름을 바꾸는 건 지우는 것만큼 목록을 무력화한다**
- [x] 인덱스에 `id` 명시 + V3 설명 정정 (purge된 행을 읽지는 않는다)
- [x] 비밀번호 형식 — 강제되는 둘과 권장만 하는 하나를 문서에서 구분

### 검증

건수는 `docs/00-requirements-traceability.md`의 「검증 총계」에만 적는다.

- [x] **실패를 먼저 재현했다** — 수정 전 jar은 웹 서버 없이 돌리면 45초 타임아웃까지
      종료하지 않고(`exit=124`), 수정 후 `migrate` 프로파일은 `exit=0`
- [x] 권한 경계는 **실제 MySQL 8.4에서 CI가 매 커밋 검증**한다. 3단계 부팅과 one-shot
      종료, `01-users.sh` 실행, 자격증명 분리, 허용·거부, `SHOW GRANTS`, 재수렴까지
- [x] negative 케이스가 비어 있지 않은지 — `sql_as`를 스텁으로 갈아 끼워 세 분기 확인.
      그래서 **job이 초록이라는 사실 자체가 거부가 일어났다는 증거**가 된다
- [x] 비밀번호 필터를 경계값으로 확인 (따옴표·역슬래시·공백·`$`·빈 문자열 거부)
- [x] `ALTER TABLE ... DROP INDEX`가 H2 MySQL 모드에서 도는지 **가정하지 않고 실행해 확인**
- [x] `gradlew test` / `verify.sh` / `ui-verify.mjs` 전부 통과, 실패 0

### 아직 확인하지 못한 것

**`EXPLAIN`으로 MySQL 옵티마이저가 V4 인덱스를 실제로 고르는지** 하나뿐이다. H2 테스트와
CI가 증명하는 것은 마이그레이션이 그 순서의 인덱스를 만든다는 것까지이고, 인덱스 설명도
구조에서 따라 나온 것이지 측정한 것이 아니다. 데이터가 쌓인 뒤에나 의미가 있다.
