## 현재: 오늘 배포 — 호스트 포트 충돌 해소

배포 대상 인스턴스는 nginx가 80/443을, 다른 프로젝트가 8080·8081을 이미 쓰고 있다.
그런데 compose가 호스트 포트를 `127.0.0.1:8080`으로 **하드코딩**하고 있어 `docker compose
up`이 `port is already allocated`로 실패한다. 환경변수가 없어 `.env`로 피해갈 수도 없다.
**배포를 막는 것은 이것 하나뿐이었고, 나머지는 설정과 순서 문제다.**

- [x] `- "127.0.0.1:${APP_HOST_PORT:-8080}:8080"` — 호스트 쪽만 변수로. 컨테이너 안은
      항상 8080이라 `EXPOSE`·헬스체크·Caddyfile은 그대로
- [x] `.env.example`·`deploy/README.md`·`docs/04-deployment.md`에서 "8080에 바인딩한다"는
      **단정을 설정값 서술로** 바꾸고, nginx 리버스 프록시 예시 추가 (지금까지 Caddy 경로만
      문서화돼 있었다)
- [x] `verify-grants.sh`가 **기본값이 아닌 18080**으로 스택을 띄운다. 기본값으로만 돌면
      이 변수가 존재하는 이유인 치환 경로를 한 번도 실행하지 않는다
- [x] 프론트 두 곳을 실제 도메인으로 — `index.html`의 `api-base`, `vercel.json`의 CSP

### 계획에 없었는데 발견한 것

**`index.html` 주석이 "Vercel이 환경마다 이 값을 바꿔 쓴다"고 적고 있었다.** 그런 장치는
없다. 빌드 단계가 없으므로 Vercel은 커밋된 파일을 그대로 낸다 — 문서 쪽은 "배포 전에 직접
고치라"고 정확히 안내하고 있었으니, 주석만 실제보다 셌다.

그래서 커밋된 값이 운영 주소가 되어야 하는데, 그러면 **로컬 브라우저 검증이 운영 API를
때린다.** 실제로 그렇게 됐다(`ERR_TUNNEL_CONNECTION_FAILED`, 체크박스 0개). `ui-verify.mjs`가
문서 파싱 중에 태그를 고쳐 쓰도록 했다. 요청 가로채기로 같은 일을 하려다 페이지의 첫 API
호출이 매달리는 것을 봤다 — 미리 깔린 Chromium과 playwright 리비전이 다른 탓이고, 자세한
것은 `tasks/lessons.md` 12번.

**그리고 `ui-verify.mjs`는 `ADMIN_TOKEN`을 받아 자기 fetch에만 쓰고 브라우저에는 주지
않았다.** 토큰이 설정된 API에서는 화면의 모든 쓰기가 401이 된다. 배포될 API는 토큰이
설정된 쪽인데 검증은 꺼진 쪽만 보고 있었다.

**헬스체크가 재던 것이 의존자가 쓰는 것과 달랐다.** CI가 이 PR에서 빨간불이 나서 알았다.
`mysqladmin ping -h localhost`는 **유닉스 소켓**으로 붙는데, mysql 이미지는 초기화 스크립트를
도는 동안 `--skip-networking`으로 임시 서버를 띄운다. 그래서 TCP가 닫힌 채로 healthy가 되고,
`depends_on`이 migrate를 풀어줘서 `mysql:3306`에 `Connection refused`가 났다. 로그의 시각이
그대로 말해 준다 — 빈 볼륨에서 기동 **5.5초 만에** healthy, 3.5초 뒤 migrate 실패.

`-h 127.0.0.1`로 바꿔 TCP를 강제했다. 초기화 중에는 이 검사가 실패하므로 진짜 서버가 3306에
붙은 뒤에야 healthy가 된다. **PR #5의 CI는 운으로 통과한 것이었다.**

### 리뷰 대응 — 1건

**로컬 실행에서 API 주소를 설정할 경로가 없었다.** 커밋된 `api-base`를 운영 주소로 채운
뒤, 나는 그 부작용을 `ui-verify.mjs` 안에서만 막았다. 그래서 **README 빠른 시작을 따라가는
사람은 로컬 백엔드를 띄워 두고 브라우저는 운영 API를 부르게 된다.** 자동 검증만 초록이고
문서가 시키는 대로 한 사람은 깨지는 상태였다.

- [x] 로컬에서 서빙된 페이지는 태그를 무시하고 `localhost:8080`(또는 `?api=`)을 쓴다.
      태그로 되돌아가지 않는 것이 요점 — 그 값이 바로 로컬 페이지가 닿으면 안 되는 주소다
- [x] `?api=`는 **로컬 페이지에만** 적용된다. 관리자 토큰이 `API_BASE`로 헤더에 실려
      나가므로, 배포된 오리진에서 허용하면 링크 하나로 남의 토큰이 흘러간다
- [x] `ui-verify.mjs`가 `MutationObserver` 대신 **사람과 같은 `?api=`**를 쓴다. 검증이
      문서가 안내하는 경로를 지나가므로, 그 경로가 망가지면 브라우저 검증이 빨간불이 된다
- [x] README 빠른 시작에 반영

### 리뷰 대응 — 2건

**2. 삭제 방지 검사가 볼륨 하나를 빠뜨렸다 (P1).** `extguard_mysql-data`만 보고
`extguard_uploads`는 보지 않아서, 컨테이너와 DB 볼륨이 없고 업로드 볼륨만 남은 기계는
그냥 통과하고 `down -v`가 파일을 지웠다.

**볼륨을 하나 더 세는 대신 격리로 바꿨다.** 위험의 원인은 검증이 배포 스택과 *같은
프로젝트 이름*을 쓴다는 것이었다. `-p extguard-verify`가 파일의 `name: extguard`를
이기므로 볼륨이 `extguard-verify_*`가 되고, 지울 수 있는 것이 자기가 만든 것뿐이 된다.
**목록은 어긋날 수 있지만 격리에는 맞출 목록이 없다.**

가드 자리에는 **격리 자체를 확인하는 단언**을 넣었다. 실효 프로젝트 이름을 compose에서
읽어 배포 이름과 같으면 종료한다. 나중에 누가 `-p`를 빼면 그 편집이 여기서 실패한다 —
누군가의 업로드가 지워지는 방식이 아니라. `config`는 데몬이 필요 없어 매 실행마다 돌고,
CI도 같이 돈다.

- [x] 태그를 고쳐 쓰지 않으면 정말 운영으로 가는지 **확인했다** — 브라우저가

      것도 확인
- [x] **제한이 실제로 걸리는지도 확인했다** — 비로컬 오리진(`127.0.0.2`)에서 `?api=`를
      실어 열었더니 무시되고 배포 주소를 썼다. 이 단언이 없으면 "로컬만 적용"은 주장일 뿐이다
- [x] **격리를 argv로 확인했다** — `docker`를 스텁으로 갈아 끼워 전 실행을 기록했더니
      호출 5건이 전부 `-p extguard-verify`였고 배포 프로젝트를 겨냥한 것은 0건.
      볼륨을 지우는 호출도 `extguard-verify` 하나뿐이다
- [x] **`-p`를 빼 보았다** — 단언이 작동해 `down -v`가 한 번도 돌기 전에 종료(exit 1).
      처음 만든 하네스는 복사본이 다른 디렉터리를 가리켜 엉뚱한 분기를 쟀고, 저장소
      안에서 다시 돌려 확인했다
- [x] 헬스체크 수정 후 CI 재실행 — 두 job 초록, 권한 경계 31건

### 아직 확인하지 못한 것

- **이 기계에 Docker 데몬이 없어 `verify-grants.sh`를 돌리지 못했다.** 18080으로 바꾼 것이
