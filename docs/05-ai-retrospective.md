# AI 활용 회고

무엇을 만들었는지는 다른 문서에 있습니다. 이 문서는 **AI가 낸 결과를 어떤 기준으로
받아들이고, 고치고, 버렸는지**만 적습니다. 각 항목의 상세 경위는
[`01-decisions.md`](01-decisions.md), 재발 방지 규칙은
[`../tasks/lessons.md`](../tasks/lessons.md)에 있으므로 여기서 되풀이하지 않습니다.

## 기준 한 줄

**그 자리에서 틀린 것을 볼 수 있으면 그대로 썼고, 볼 수 없으면 볼 수 있게 만든 뒤에 썼다.**

컴파일 실패, 빨간 테스트, 실행 결과, 명세 원문이 그 "볼 수 있는 수단"이었습니다. 수단이
없는 산출물(특히 **문서 문장과 코드 주석**)은 채택 대상이 아니라 확인 대상으로 뒀습니다.
이 프로젝트에서 실제로 위험했던 것은 틀린 코드가 아니라 **틀린 것을 볼 수 없게 만든 검증**
이었습니다.

## 그대로 쓴 것

틀리면 즉시 드러나는 자리였기 때문입니다.

| 항목 | 그대로 쓴 근거 |
|---|---|
| Spring Boot 4.1 이행 세부(`starter-webmvc`, Jackson 3, `webmvc-test` 분리, BOM 임포트) | 틀리면 **빌드가 깨진다.** 채택 비용이 낮고 오판이 즉시 보임 |
| 파일명 처리 케이스 표(대소문자·이중 확장자·후행 점·예약 장치명·경로 성분) | 각 항목이 한 줄 테스트로 고정됨. 주장과 검증이 1:1 |
| 확장자 정규화 5단계(NFKC → trim → 선행 점 → `Locale.ROOT` → 문자셋) | 같은 이유. 터키어 로케일 건도 테스트로 박제 |
| 거부 응답 3단 구조(`message`/`detail`/`code`) | 요구사항에 대응하는 구조 결정이고, 브라우저 검증이 화면 문구까지 읽음 |
| 무료 티어·EOL 조사 결과(OCI 한도 반감, Boot 3.5 EOL, 무료 MySQL 부재) | 출처가 있고 **결정을 실제로 뒤집는 사실**이었음. 검색 없이 갔으면 EOL 프레임워크로 시작 |

## 고쳐 쓴 것

| 초안 | 고친 결과 | 왜 |
|---|---|---|
| `type` 컬럼 한 테이블로 고정/커스텀 구분 | 테이블 분리 + CHECK 2종 + 리포지토리 분리 + 권한 축소 | 고정성이 **스키마 불변식이 아니라 컬럼 값**이었음 |
| R5 = "내용이 실행 파일이면 무조건 거부" | R5 = **위장 탐지**(정직한 선언이면 확장자 정책에 위임) | 아니면 `exe` 체크박스가 지키지 못할 약속을 함 |
| CAFEBABE를 바이트 값 범위로 Java/Mach-O 구분 | 항상 모호로 보고 → 정직 판정 불가 | 공격자가 고르는 값에 기댄 휴리스틱 |
| 쿼터 경합 초과량을 수치로 단언 | 기호 정의 → 식 유도 → **표를 그 식으로 검산** | 같은 수치를 두 번 틀렸음 |
| 검증 건수를 네 문서에 복사 | 추적표 「검증 총계」 단일 출처 | 복사본이 **세 번** 어긋남 |
| "확인할 수단이 없다"는 한계 서술 | CI에 MySQL 권한 경계 잡 추가 | 세션에 Docker가 없던 것이지 프로젝트에 없던 게 아님 |

## 버린 것

| 버린 것 | 이유 |
|---|---|
| `io.spring.dependency-management` 플러그인 | Boot 4에서 동작하지 않음 → `platform()` BOM |
| MIME 타입을 거부 근거로 쓰기 | 공격자가 바꿀 수 있고 정상 파일도 자주 틀림 → 보안은 안 늘고 오탐만 늚. 기록만 |
| `msi`·`bin`·`out`의 "정직한 선언" 자격 | "실행 파일 계열"은 기준이 아님. 기준(확장자가 형식을 이름 짓는가)을 정하고 재판정 |
| 정책 캐시 | 조회 규모가 작고, "체크 직후 즉시 반영"이 이 시스템의 핵심 요구 |
| 프론트 업로드 라이브러리 | 클라이언트 검증은 어차피 신뢰 불가 → 공급망·CSP 비용이 이득보다 큼 |
| `security-review` 스킬로 사후 점검 | 여기서 보안은 사후 점검 대상이 아니라 **요구사항 그 자체**라 설계 단계에서 다룸 |

## AI가 놓쳤고 리뷰에서 잡아낸 것

이 프로젝트에서 설계를 실제로 바꾼 것은 대부분 이쪽입니다.

| 지적 | AI가 하고 있던 것 | 왜 스스로 못 잡았나 |
|---|---|---|
| "외부에서 고정 확장자를 지우거나 고정이 아닌 상태로 만들 수 있나" | 서비스 코드의 `if` 하나로 고정성 보장 | **중복 방지**(UNIQUE) 논리를 **고정성 보장**의 근거로 착각 |
| "exe는 실행 파일이니 체크를 풀어도 막히는 것 아닌가" | 정책 화면이 강제되지 않는 상태 | 모든 `hello.exe` 픽스처가 텍스트라 **그 분기에 들어가 본 적이 없음**. 테스트는 전부 초록 |
| "`js`는 왜 없나 — exe와 같은 오류 아닌가" | 고정 확장자 7개 중 하나에 같은 버그가 남아 있었음 | 한 건을 고치고 **같은 형태를 전수로 훑지 않음** |
| "`.msi`는 PE가 아닌데 왜 여기 있나", "`.out`은 기준이 뭔가" | 목록을 "계열"로 늘려 둠 | 기준을 적지 않으면 목록은 계속 느슨해짐 → `bin`·`out` 연쇄 제거 후 기준 명문화 |
| "모호한 시그니처를 허용 확장자로 덮는 건 R5를 무의미하게 만든다" | 관찰(`현실의 fat은 2~6개`)을 제약처럼 서술 | **명세 원문을 확인하지 않음**(`nfat_arch`에 상한 없음) |
| "업로드를 무한히 쌓기만 한다" | 상한·회수·부분 파일 정리 전무 | 기능 요구만 보고 **운영 수명**을 보지 않음 |
| "계정을 나눈 것과 권한을 분리한 것은 다르다" | 앱이 마이그레이션 자격증명을 그대로 들고 있었음 | 검증이 "앱이 뜬다"를 재고 **"강한 계정을 갖고 있지 않다"**를 재지 않음 |
| 배포 화면에서 토큰 없이 토글 → "서버에 연결할 수 없습니다" | 필터가 끊는 401에 CORS 헤더가 없었음 | 세 계층이 **같은 눈**이었음 — MockMvc·curl은 CORS를 강제하지 않고, 브라우저 검증은 토큰을 항상 심고 시작 |
| "보장/원자적/불가능이 실제보다 세다" | PR 하나에서 네 문장이 코드보다 강하게 보장 | 정상 경로 관찰을 명세처럼 적음 |

## 반복된 실패 형태 세 가지

개별 오류보다 이 세 가지가 반복됐고, `tasks/lessons.md`는 사실상 이 셋의 변주입니다.

1. **강한 단어** — "구조적으로", "원자적", "불가능하다"를 관찰만으로 씀.
   → 단정할 때마다 근거가 명세인지 내가 본 정상 경로인지 그 자리에 밝힌다.
2. **커버리지 착시** — 초록인 테스트가 그 규칙에 진입조차 안 하거나, 앞 단계의 부수
   효과로 통과함. → 새 검증을 만들 때 **"이 계층이 앞 계층과 무엇을 다르게 보는가"**를
   적고, 옛 코드로 되돌려 **빨간불이 켜지는 것**을 본다.
3. **정정 과잉** — 느슨한 문장을 고치다 반대쪽으로 넘어감(프리뷰 CORS 건).
   → 정정은 원래 문장이 틀린 만큼만 움직이고, 고친 문장도 새 문장과 같이 검문한다.

## 이 방식으로 실제로 바뀐 것

- 검증을 **늘리는 대신 서로 다른 것을 보게** 만들었습니다(테스트 / curl / 브라우저 /
  실제 MySQL 권한). 건수는 추적표 한 곳에서만 셉니다.
- 고정 확장자 목록은 **데이터가 아니라 코드**가 됐습니다. DB 행이 지워져도 화면은 7개입니다.
- 지적을 받을 때마다 코드만 고치지 않고 **그 지적을 다음에 기계적으로 잡는 수단**
  (테스트·CI 잡·문서 규칙)을 같이 넣었습니다. 커버리지 공백은 수정의 일부지 후속이 아닙니다.
